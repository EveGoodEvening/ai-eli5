LLM inference · Prefill / Decode

Before AI answers, it reads everything, then writes one token at a time.

Reading is called prefill. Writing is called decode. Tell them apart and you'll know where AI gets slow.

A token is a small chunk of text — roughly a word or part of one.

→

01

Waiting for AI really means waiting for two things

How long until it starts? How fast does it write after that?

TTFTSlow to start?The wait before the first token: mostly prefill, plus any queueing or transfer.
ITLSlow once it starts?The gap between tokens: that comes from decode.

02 · PREFILL

Prefill: read the whole input first

Only want three takeaways? Those dozens of pages still have to be read first.

The input is all known → no need to queue token by token; compute it as one block.

Every layer does this, then hands off to the next. After the last layer, the final position predicts the first new token.

03

If token 2 needs token 1’s information, how can they be computed together?

Position 2 needs K₁/V₁ (ready right away), not position 1’s result O₁ → both rows can run together.

Layers still go in order: this layer’s output is the next layer’s input.

04 · DECODE

Decode: write one, feed it back, write the next

The token just written becomes the next step’s input. Try it ↓

Input read; first token picked: “Boss”. The cache still has 4 slots — the K/V for “Boss” appears only after it is fed back into the model.

The document’s K/V stays putNo need to recompute the whole document for every new token. Each step still reads those K/V, though.
Why not write it all at once?The next token isn’t known yet — this one must be picked first to become the next input.

05

Long report vs. long speech: slow in different places

The shapes compare only how much goes in and out — they are not measured times.

06

Same model, two different jobs

Every step moves the model’s weights from memory to the compute units.

Prefill: one trip, many rows. Decode: one trip, one row.

A common tendency (a single request, small batches), not a law: bigger batches, different models or kernels can all move the bottleneck. And the longer the context, the more past K/V each step must read — a fast start doesn’t guarantee a fast finish.

See “xx tokens per second”? Ask three questions first:

01How long is the input?
02How long is the reply?
03How many people at once?

Identical opening, KV still kept → reuse it directly (prefix caching).

The new question still needs prefill; the new answer still needs decode.

09

One machine reads, another writes?

EXO demonstrated it: a DGX Spark runs prefill, then a Mac Studio M3 Ultra carries on with decode.

Early layers’ KV ships out while later layers compute → transfer and compute partly overlap.

A third-party (EXO) demo; the illustration is not a measurement. Data still in flight at the end and format conversion still take time, and both sides need compatible models, position handling, and cache formats.
